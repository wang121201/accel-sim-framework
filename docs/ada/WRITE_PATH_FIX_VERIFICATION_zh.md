## 四、⚠️ 两类仍需说明的差异

### 4.1 硬件写 = 0，模拟写 > 0（`l2train_*`、`l2hold_*`，共 6 格）

**现象**：硬件 NCU 测得 `dram__bytes_write.sum = 0`，但模拟器现在报非零写。

**原因**：这些微基准的**输出缓冲区极小**。
以 `l2train_m8_p8_b48_t32_i1` 为例：
```
output[chain * workers + worker] = sums[chain];   // memory_concurrency_probe.cu:93
```
- grid = 48 blocks × 32 threads = 1,536 workers
- 每 worker 写 4 B（ILP=1）→ 输出总量仅 **6 KB**
- 6 KB 远小于 40 MB L2 → **脏行全部驻留 L2，硬件确实不写 DRAM**

**模拟器为何有写？** 模拟器把 store 经 L1（WRITE_THROUGH）送到 L2，
L2 做 write-allocate；部分行因**地址映射/组冲突**被淘汰并写回。
即：模拟器的写回比硬件"多"。

> ⚠️ 这是**模拟器侧的行为差异**，不是修复引入的 bug（修复前是 0，
> 属于"丢写回"；现在是"多余写回"）。**方向相反但都偏离硬件**。
> 根因指向 **L2 组映射/替换策略**与真实 Ada 不一致 —— 与 `indexing=0`
> 的补偿性近似同源。

### 4.2 硬件写 ≫ 模拟写（`dramtrain_*`，4 格）

| 用例 | 硬件写 (B) | 模拟写 (B) | ratio |
|---|---:|---:|---:|
| `dramtrain_..._b48_t32_i1` | 1,385,984 | 3,072 | 0.002 |
| `dramtrain_..._b192_t32_i1` | 1,448,576 | 17,760 | 0.012 |
| `dramtrain_..._b48_t256_i1` | 1,459,584 | 73,536 | 0.050 |
| `dramtrain_..._t32_i4` | 1,336,448 | 21,984 | 0.016 |

**原因**：模拟器 L2 容量 40 MB，而这些单 kernel 微基准的工作集更小，
**多数脏行在 kernel 结束前未被淘汰**。硬件上这些写最终仍会落到 DRAM
（NCU 的 ROI 窗口包含排空），模拟器则停在 L2 内。

> 这是**工作集/ROI 边界性质**，不是丢写回。要完全对齐需多 kernel
> 负载或超容量工作集。
